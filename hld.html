Networking & Edge Delivery

DNS · Load Balancer · CDN · Proxies
The Big Picture
System Design (HLD) is the art of planning how large applications survive massive real-time traffic without crashing or slowing down — like crores of people watching the last over of a cricket final on Hotstar at the exact same second. It brings together Networking, APIs, Caching, Databases, Scaling, and Security into one working blueprint.

What Actually Happens When You Tap an App? (DNS Resolution)

IPv4 = 32-bit · IPv6 = 128-bit

Computers talk to each other using numeric IP addresses (like 142.250.193.78), not domain names. Since humans can't memorize strings of numbers for every website, DNS (Domain Name System) acts like the internet's phonebook — translating friendly names like api.hotstar.com into the exact server IP behind the scenes.

1
App Loads into RAM Your phone's OS loads the app into RAM (running code always lives in RAM) and checks for internet. If offline, it shows locally cached content or an error. If online, it prepares an API call like GET api.hotstar.com/homefeed.
2
Check Local Caches First Before searching the whole internet, the system checks fast caches in order: Browser Cache → OS Cache → ISP Resolver → Public DNS (Google 8.8.8.8, Cloudflare). Most everyday lookups end right here.
3
Recursive DNS Lookup If the IP isn't cached anywhere, a recursive resolver hunts it down step-by-step: asks the nearest Root Server (13 global clusters) → points to the TLD Server (.com) → points to the Authoritative Nameserver, which returns the true IP.
4
Enter via Load Balancer Once your device has the IP, the request still doesn't go straight to an application server. It first hits a Load Balancer (or CDN edge), which safely routes it to a healthy backend machine.

Load Balancers — Keeping Servers Alive Under Traffic

Propagation Delay = Distance ÷ Signal Speed + Algorithms Added

If millions of users hit a single server, its CPU and RAM max out and the app crashes. A Load Balancer sits at the front door like a traffic police officer, spreading incoming requests across a fleet of backend servers. If one server dies, it automatically stops sending traffic there so users never notice an outage. It can even cache hot items (like a viral trailer) and reply directly without bothering the backend.

Content Delivery Network (CDN)

Serving Data From Down the Street
Simple Analogy
Think of Blinkit / Instamart vs. traditional Amazon. Amazon keeps stock in big central warehouses (1–3 days delivery). Blinkit places small dark stores in every neighborhood so items arrive in 10 minutes. A CDN does the exact same thing for videos, photos, and web files — keeping copies on local Edge Servers close to users instead of fetching from a faraway Origin Server in another continent.
How a CDN Request FlowsCache Hit vs Miss

When you open a video or website, DNS doesn't give you the origin server's IP — it resolves directly to the nearest CDN edge server.

  • Cache Hit (~20 ms): The edge server already has a copy of the file and sends it back almost instantly.
  • Cache Miss (~2500 ms): The file isn't at the edge yet, so the edge fetches it from the distant origin server, hands it to you, and saves a copy locally so the next nearby user gets a fast hit.
  • Built-in Reliability: If your nearest edge server crashes, requests smoothly fall over to the next-nearest healthy edge server.
Why Even an 80% Hit Rate Is HugePull vs Push CDN

Suppose an origin fetch takes 2500 ms and an edge fetch takes 20 ms. Over 100 requests:

  • Without CDN: All 100 hit origin → 250,000 ms total (2,500 ms average per request).
  • With 80% Hit Rate: 80 hits (1,600 ms) + 20 misses (50,000 ms) = 51,600 ms total → 516 ms average (~5× faster!).
  • Pull vs. Push: Most CDNs are Pull (fetch automatically on first miss and expire via TTL). Push CDNs let you pre-upload files ahead of a big launch so even the very first user gets a hit.

Forward Proxy vs. Reverse Proxy

Client's Bodyguard vs. Server's Bodyguard

A proxy is simply a middleman that stands between a sender and a receiver. The only thing that separates a forward proxy from a reverse proxy is whose side it sits on and who it protects.

Forward Proxy (Client-Side)Squid · VPNs

Sits between you (the client) and the internet. Websites only see the proxy's IP address, never your real IP.

  • Content Filtering: Colleges and offices route student/employee traffic through a forward proxy to block sites like Facebook before requests even leave the network.
  • Privacy & Bypass: Masks your IP or geographic region. Using a VPN to bypass a college block is simply using your own forward proxy instead of theirs.
  • Local Caching: Caches popular pages inside an institution so 500 students don't re-download the same file from the internet.
Reverse Proxy (Server-Side)NGINX · HAProxy

Sits between the internet and a company's backend servers. Users don't even know it's there — it hides internal server IPs and shields the backend.

  • Load Balancing & Caching: Spreads incoming requests across backend machines and replies directly for cached pages.
  • SSL/TLS Termination: Handles heavy HTTPS decryption at the front door so internal traffic between the proxy and backend servers can travel fast over plain HTTP inside a private network.
  • Security & Compression: Blocks DDoS floods and SQL injection attempts, and compresses responses (Gzip/Brotli) to save bandwidth.

APIs, Gateways & Communication Protocols

API Gateway · SDK · REST · GraphQL · gRPC · WebSockets · Webhooks

API, API Gateway & SDK — How They Differ

The internet physically connects your phone (frontend) to a company's servers (backend), but an API defines the exact rules for how they talk — what requests are allowed and what responses look like. In big apps like Netflix or Swiggy, dozens of separate backend services run in parallel (Auth, Search, Payments, Recommendations), so an API Gateway stands in front as a single reception desk.

API Gateway — The Front DeskKong · AWS API GW

Instead of making your mobile app know the addresses of 20 internal microservices, every request enters through one API Gateway.

  • Smart Routing: Sends /login to Auth Service and /pay to Payment Service.
  • Upfront Security: Checks JWT/OAuth tokens and enforces rate limits before a single bad request touches your backend.
  • Quick Shortcuts (Caching): If a response is already cached, the gateway returns it right away — like a Zomato delivery partner picking up a packed order at the counter without sitting down to order.
Design rule: Always keep the API Gateway stateless (no local session storage) so you can scale it horizontally under spikes.
API vs. SDK — Waiter vs. Full KitchenBuild Faster

When building a house, you don't manufacture your own cement or electrical wires — you buy ready-made materials. Software works the same way.

  • API = The Waiter: Just the communication channel carrying a request to a server and bringing back a response.
  • SDK = The Fully Equipped Kitchen: A complete developer toolkit (libraries, helper functions, sample code, docs) for plugging in a whole feature — like Razorpay payments, Google Maps, or Gemini AI — in minutes.
  • Under the hood: An SDK still calls the provider's APIs internally; it just spares you from writing the raw HTTP plumbing yourself.

Caching & Memory Performance

RAM vs Disk · 7 Layers · Write Policies · Pitfalls

Why Databases Need a Caching Layer

Fighter Jet (Registers) → Sports Car (Cache) → Car (RAM) → Bike (SSD) → Bicycle (HDD)

Databases store data safely on disk (SSD/HDD), which takes milliseconds to read. That sounds quick until millions of users hit the database at once. A cache (like Redis or Memcached) stores hot, frequently accessed data in RAM, which responds in nanoseconds to microseconds — roughly thousands to a million times faster than disk. Because RAM is expensive and volatile (wiped on restart), we keep only high-value hot data there (user feeds, sessions, trending deals) while the database remains the permanent source of truth.

Key Clarification
Caching does not just mean Redis! It is a universal idea applied at 7 points along a request's journey: (1) DNS Cache at your browser/ISP, (2) Client/Device Cache for logos & recent chats, (3) Forward Proxy Cache in colleges/offices, (4) CDN Edge Cache for videos & thumbnails, (5) Reverse Proxy Cache for API/HTML responses, (6) Application Cache (Redis) for dynamic feeds/sessions, and (7) Database Query Cache for heavy repeated queries.

How Reads & Writes Stay in Sync

+ Cache-Aside & Write-Around Added

Reading from a cache is simple: if the item is there (Cache Hit), return it immediately without touching the database; if not (Cache Miss), fetch from the database and store a copy in the cache. The tricky part is writes — when a value changes from x = 100 to x = 200, when does the underlying database get updated?

StrategyHow It WorksBest AdvantageMain Trade-off / Risk
Cache-Aside Your app code checks the cache first. On a miss, your app reads from the DB, saves the result into the cache with an expiry (TTL), and returns it. Most popular Only actually requested data takes up RAM, and if Redis goes down, your app still works (just slower via DB). The very first read is always a slow miss, and cached data can be slightly stale until its TTL expires.
Write-Through Every time data is updated, it is written to the cache and the database/main memory at the exact same time before confirming success. Always consistent Both copies match at every moment, so no data is lost if the cache crashes. Slower writes because every update has to wait for two separate writes to finish.
Write-Back Updates hit only the cache right away and mark the block with a Dirty Bit = 1 ("modified, needs saving"). A background worker flushes dirty blocks to memory/DB later in batches. Super fast writes Absorbs huge write bursts cleanly (this is why YouTube/Instagram like counts update on your screen immediately while the admin panel catches up seconds later). Data loss risk Brief inconsistency between cache and DB — and if the cache crashes before flushing dirty blocks, those pending edits vanish.
Write-Around Writes go straight to the database, skipping the cache completely. Data enters the cache only later if someone reads it. Keeps rarely-read write-once items (like logs or old messages) from kicking out genuinely hot data from RAM. If a user writes something and immediately reads it back, they hit a cache miss.

Eviction & Real-World Cache Pitfalls

+ Interview Must-Knows
When RAM Fills Up (Eviction)Making Room
  • LRU (Least Recently Used): Kicks out whichever item hasn't been touched for the longest time. Great all-around default.
  • LFU (Least Frequently Used): Kicks out items with the fewest total hits — handy when a sudden one-time scan shouldn't push out evergreen popular items.
  • TTL (Time To Live): Automatically deletes a key after a set time (say, 5 minutes) so stale data doesn't linger forever.
3 Ways Caching Can Crash Your DBAnd How to Fix Them
  • Cache Stampede (Thundering Herd): One super-hot key expires and 10,000 users hit the DB at the exact same instant. Fix: Let only one request rebuild the cache (lock) while others wait, or refresh proactively before expiry.
  • Cache Penetration: Bots request fake IDs (user_-999) that exist nowhere, bypassing cache straight to DB. Fix: Cache "not found" briefly or put a Bloom Filter in front.
  • Cache Avalanche: Thousands of keys share the same TTL and expire together. Fix: Add random jitter (e.g., 5 min ± 30 sec) to every TTL.

Databases, Storage & Distributed Data

SQL vs NoSQL · Partitioning · Sharding · Replication · CAP · ACID/BASE

SQL vs. NoSQL — How to Pick the Right Database

Never give a flat "SQL is better" or "NoSQL is better" answer

In interviews and real engineering, you pick a database by asking six practical questions: Is the data structured or variable? Is traffic read-heavy or write-heavy? Does a wrong number lose money (strict consistency) or is a 2-second delay fine? Do we need complex multi-table joins? And how big are the traffic spikes (like Big Billion Days)? Real apps like Amazon almost always combine several databases together — PostgreSQL for orders/payments, MongoDB for flexible product catalogs, Redis for hot homepage deals, and S3 + CDN for product images.

Partitioning vs. Sharding vs. Replication

Three distinct tools people constantly mix up

When a table grows to a billion rows, scanning all of it on every query grinds your app to a halt. Here is the clean mental split: Partitioning organizes data inside one server, Sharding splits data across multiple servers (great for writes), and Replication makes full copies across servers (great for reads and backups).

1. PartitioningSame DB Server

Splits a huge table into smaller chunks on the same machine — like adding separate Veg, Non-Veg, and Dessert counters inside one restaurant.

  • Horizontal: Split by rows (e.g., 10k rows per chunk).
  • Vertical: Split by columns (keep frequently read "hot" columns separate from rarely used "cold" columns).
  • How rows get routed: Range (orders by year), List (by country: India/US/Japan), or Hash (user_id % 4 for even spread).
Limit: Low network overhead and easy to manage, but still capped by one server's hardware (like vertical scaling).
2. ShardingMultiple DB Servers

Splits your data across separate independent servers (shards) — like opening completely new restaurant branches in Delhi, Tokyo, and New York.

  • Shines for Write-Heavy Apps: In WhatsApp or Instagram, a new post from North India writes only to the North shard — no need to coordinate with other shards.
  • Near-limitless scale: Just add more shards as data grows (horizontal scaling).
  • The Pain Points: Queries needing data from multiple shards (cross-shard joins) are slow and complex, and popular keys can overload one shard.
3. ReplicationFull Copies

Creates complete copies of your database on other servers using a Leader (Master) → Follower (Replica) setup.

  • Shines for Read-Heavy Apps: When Netflix drops a hit movie, millions of reads spread across replicas so the primary DB stays calm.
  • High Availability: If the Leader crashes, a Follower gets promoted so the app stays online.
  • Sync vs Async: Synchronous updates every replica immediately (strictly consistent, slower writes). Asynchronous updates replicas moments later (fast writes, slight lag).
In production: Big companies use both — shard the data, then replicate each shard!

Consistent Hashing & Database Indexing

+ Core HLD Additions
Why Simple key % N Breaks — Consistent HashingSmart Sharding

Suppose you shard keys across 4 servers using user_id % 4. The day you add a 5th server (% 5), almost every single key maps to a different server — triggering massive data migration and wiping out your cache hit rate!

Consistent Hashing fixes this by arranging servers and keys on a circular Hash Ring (0 to 2³²-1). Every key belongs to the first server found moving clockwise. Now, adding or removing a server only moves keys from its immediate neighbor (~1/N of data). Adding Virtual Nodes (placing each server at several spots on the ring) keeps the load evenly balanced.

Database Indexing: B-Tree vs. LSM-TreeFast Lookups

An index is like a book's index page: instead of scanning 1 billion rows one by one (O(N)), the DB jumps straight to the record in O(log N). The trade-off: every write gets slightly slower because the index must also be updated.

  • B-Tree (PostgreSQL, MySQL): Updates pages in place. Predictable, fast reads and range queries.
  • LSM-Tree (Cassandra, RocksDB): Appends new writes sequentially into RAM first, then flushes sorted files to disk in batches. Built for massive write throughput.

CAP Theorem & ACID vs. BASE

The fundamental trade-off of distributed data
CAP Theorem (Distributed DBs)CP vs AP

When data lives across servers in Delhi and Mumbai connected by a network, network cables will occasionally break (a Network Partition). Because Partition Tolerance (P) is unavoidable in the real world, you must choose what happens during a split:

  • Choose CP (Consistency + Partition Tolerance): Refuse requests rather than risk showing stale/wrong data. Essential for banking & payments — after withdrawing ₹20,000, no ATM may ever show the old balance.
  • Choose AP (Availability + Partition Tolerance): Always give the user a response, even if it's a few seconds behind. Ideal for Instagram likes or WhatsApp counts — a brief stale count is way better than an error screen.
ACID vs. BASEBanking vs Social Media
  • ACID (Strict Correctness — SQL): Atomicity (a transfer either finishes completely or rolls back — no half-done debits), Consistency (if A has ₹100 and B has ₹200, transferring ₹50 still keeps total ₹300), Isolation (concurrent transactions don't step on each other), Durability (committed data survives power cuts).
  • BASE (Massive Scale — NoSQL): Basically Available (system stays responsive), Soft State (values across servers may briefly differ while syncing), Eventually Consistent (view count might flicker 10,000 → 10,050 → 10,020, then settle to the true number).

Vertical Scaling vs. Horizontal Scaling

1 Super-Waiter vs. 10 Regular Waiters

Imagine hosting a party for 50 guests. You can either hire one superhuman waiter and push them harder (Vertical Scaling / Scale-Up: upgrading one server from 8 GB → 128 GB RAM and 4 → 32 CPU cores), or hire ten normal waiters to share the tables (Horizontal Scaling / Scale-Out: adding more servers behind a Load Balancer).

Microservices & Message Queues

Divide work & decouple slow tasks
Microservices, Containers & KubernetesMonolith → Modular

A single shop trying to sell groceries, medicines, restaurant meals, and electronics under one roof becomes pure chaos on a weekend rush — that's a Monolith. In a Microservices setup (like Blinkit), you split the system into focused, independently deployable services: User, Catalog, Cart, Dark-Store Inventory, Payment, Delivery, and Notifications.

  • Containers (Docker): Pack each service's code and dependencies in its own isolated box so it runs identically everywhere.
  • Kubernetes (K8s): Automatically orchestrates those containers — if Search gets 10× traffic, K8s scales only Search without wasting money scaling Billing.
  • Right DB per service: User data can use PostgreSQL while variable product catalogs use MongoDB.
Message Queues (Async Decoupling)Kafka · RabbitMQ · SQS

During an Amazon flash sale, if checkout had to wait synchronously for Inventory, Email, SMS, and Analytics servers to finish, users would stare at a spinning wheel — or fail if the Email server went down.

  • How it works: The Order service (Producer) drops an "Order Placed" event into a FIFO queue and immediately confirms the user's order. Background services (Consumers) pull and process events at their own pace.
  • Crash-Proof & Durable: Messages are saved to disk/SSD (not just RAM) and deleted only after a consumer succeeds. If the Email service crashes for 10 minutes, messages safely wait and catch up when it returns.
  • Dead Letter Queue (DLQ): + Added Moves repeatedly failing "poison" messages aside so they don't clog the whole pipeline.

Rate Limiting — Protecting Systems From Floods

Returns HTTP 429 "Too Many Requests"

Whether it's a DDoS attacker, a ticket-scalping bot during an IPL sale, or a buggy mobile loop hammering your server, Rate Limiting caps how many requests a user/IP can make in a time window. It ensures fairness for real users and stops cloud bills from exploding. Always block excess traffic as early as possible: CDN/WAF → Load Balancer → API Gateway → App/DB backstop.

AlgorithmHow It Works (Plain English)Strengths & Flaws
Fixed Window Splits time into rigid buckets (e.g., 10 requests per clock minute). Counter resets at :00. Boundary burst bug Super cheap on memory, but a user can fire 10 requests at 12:00:59 and 10 more at 12:01:01 — sneaking 20 requests through in 2 seconds!
Sliding Window Log Saves the exact timestamp of every request and counts how many fell within the last rolling N seconds. 100% accurate Completely fixes the boundary burst exploit, but storing every timestamp eats a lot of RAM at scale.
Sliding Counter Smart hybrid: combines the current window's count with a weighted slice of the previous window. Best memory/accuracy balance Smooths out edge spikes using almost no memory (tiny approximation trade-off).
Token Bucket Imagine a bucket holding up to 10 tokens that refills steadily (e.g., 2/sec). Every request takes 1 token; empty bucket = 429. Allows healthy bursts Industry favorite (AWS, Stripe) because real users naturally click in short bursts while still obeying an average rate.
Leaky Bucket Requests enter a FIFO queue and trickle out at a strictly constant rate, like water dripping from a hole. Zero bursts allowed — smooths spiky traffic into a steady stream to protect fragile downstream backends. Overflowing requests get dropped.

Distributed Resilience Patterns

+ Essential Production Guards
Circuit BreakerPrevent Cascading Failure

Just like an electrical breaker in your home: if the Payment service starts timing out repeatedly, the breaker trips OPEN and immediately returns a fast fallback error instead of letting thousands of waiting threads freeze your entire app. After a cool-off, it tests a few requests (HALF-OPEN) to auto-heal.

Exponential Backoff + JitterSmart Retries

If a request fails briefly, don't retry instantly in a tight loop — wait longer each time (1s → 2s → 4s). Add a little random jitter (e.g., ±200 ms) so 50,000 disconnected clients don't all hammer your recovering server at the exact same millisecond.

Idempotency KeysNo Double Charges

What if a user clicks "Pay ₹500", the Wi-Fi drops, and the app retries? The client attaches a unique idempotency_key (UUID) to the payment request. If the server sees the same key twice, it returns the original result instead of charging the card a second time.

Security, TLS & Authentication

SSL/TLS · Session · JWT · OAuth · SSO · 6 Defense Layers

How SSL/TLS Certificates Actually Stop Hackers (MITM)

SSL is retired; modern HTTPS runs on TLS

Plain HTTP travels across the internet like a postcard anyone can read or edit (a Man-in-the-Middle attack). Using one shared secret key (Symmetric encryption) fails because a hacker can steal the key while you send it. Using a public/private key pair (Asymmetric encryption) is smarter, except a hacker can still intercept the server's public key in transit and swap in their own fake public key! SSL/TLS Certificates close this exact loophole using a trusted third party called a Certificate Authority (CA) like DigiCert or Let's Encrypt.

1
CA Signs the Certificate The server sends its domain & public key to the CA. The CA hashes them (H1) and encrypts H1 with the CA's own private key to create an unforgeable digital signature.
2
Server Presents Proof When you open an HTTPS site, the server sends its certificate containing its domain, public key, and the CA's signature.
3
Browser Verifies Both Hashes Your browser already trusts major CAs' public keys built into your OS. It decrypts the signature to recover H1, then hashes the received cert itself to get H2.
4
Tamper-Proof Connection If H1 == H2, the public key genuinely belongs to that website (a hacker can't forge a matching signature without the CA's private key). Both sides then agree on a fast symmetric session key for the rest of the chat.

The 6-Layer Security Blueprint ("How Do You Secure IRCTC?")

Defense in Depth across Client → Server → Database
1. AuthenticationVerify Identity

Confirm who the user is using MFA/OTP, OAuth, JWTs, or passwordless biometrics/passkeys (WebAuthn). Never save raw passwords — store strong salted hashes (Argon2/bcrypt) and compare hashes on login.

2. AuthorizationScope Permissions

Enforce what each role can touch (RBAC). In Uber, Admins, Drivers, and Riders have strictly separate privileges — a driver must never be able to access admin fare-pricing endpoints.

3. API Gateway & WAFGuard the Door

Inspect every request upfront (NGINX, Kong, Cloudflare) to validate tokens, block SQL injection/XSS payloads, and enforce rate limits before bad traffic reaches your database.

4. Data SecurityEncrypt at Rest

Never store sensitive data or backups in plain text. Encrypt databases and files using standards like AES-256 and RSA so even a leaked disk or backup stays unreadable.

5. Network & InfraEncrypt in Transit

Use HTTPS/TLS for all network traffic, isolate internal databases inside private VPCs, and lock down firewalls so only authorized backend services can reach the DB.

6. Monitoring & FraudActive CCTV

Continuously watch logs and traffic patterns for anomalies (like a user suddenly jumping from 5 transactions to 1,000/day) to catch breaches and fraud proactively.

Architecture, SOLID & Mental Models

HLD vs LLD · SOLID Principles · Restaurant Analogy

HLD vs. LLD — Zoomed-Out Map vs. Zoomed-In Code

HLD and LLD aren't separate worlds — LLD is simply zooming inside one box of your HLD diagram. Take IRCTC as an example:

HLD — High-Level DesignThe Big Picture

Focuses on major system blocks and how traffic flows between them: Authentication, Train Search, Seat Booking, Tatkal, Payment, Cancellation, and Notification microservices — connected via Load Balancers, Redis cache, SQL/NoSQL databases, and Kafka queues.

LLD — Low-Level DesignImplementation Details

Focuses on classes, schemas, and exact logic inside a service: User, Train, Coach, Seat, and PNR classes; design patterns like Factory (for UPI/Card/Wallet payments) and Singleton (shared connection); locking code to prevent double-booking; waitlist transitions; and time-based cancellation refund rules.

SOLID Principles — Writing Code That Doesn't Break When It Grows

Remodel one room without knocking down the whole house
PrincipleWhat It Means SimplyRelatable Example
S · Single Responsibility Every class should have one clear job and one reason to change. Don't stuff user signup, email sending, and activity logging into one giant class. Split them into Registration, Notification, and ActivityLog so editing emails never risks breaking signup.
O · Open / Closed Open for extension (adding new features), closed for modification (don't rewrite working code). Instead of endlessly adding else if (type == "wallet") inside a fragile Payment class, define a Payment interface and simply create new UPIPayment or WalletPayment classes.
L · Liskov Substitution A child class must work cleanly anywhere its parent is expected, without surprises. If Bird has fly(), Sparrow works fine — but Penguin or Ostrich breaks the promise! Same with putting BikeDelivery under a HeavyFurnitureDelivery parent class.
I · Interface Segregation Keep interfaces small and focused so classes aren't forced to implement useless methods. Modern smart-TV remotes beat old 60-button remotes. Don't force a basic printer to implement scan() and fax() — split into clean Printable, Scannable, and Faxable interfaces.
D · Dependency Inversion High-level business logic should depend on abstractions, not hardcoded third-party vendors. Have your Order service talk to a generic PaymentGateway interface instead of directly hardcoding Razorpay. If you later switch to Stripe or PayPal, you swap one adapter without touching core order logic.

The Restaurant Mental Model — Everything Connected

If you ever want to recall the entire flow of a distributed web application in 15 seconds, just picture dining at a popular restaurant chain:

Frontend = The menu & booking app UI | DNS = Looking up the restaurant's street address CDN = Visiting the branch closest to you | SSL & Firewalls = Entry guards, OTP & payment PIN Load Balancer = Valet assigning parking spots | API Gateway = Manager + Waiter bridging you to kitchen Cache = Pre-made mocktail (served instantly) | Database = Dish cooked from scratch (slower, authoritative) Microservices = Separate Indian/Chinese chefs | Horizontal Scaling = Opening more branches across cities Monitoring & Logs = CCTV & kitchen audits | Feedback Loop = Post-meal ratings to improve service

Case Study 1: Designing Instagram (500M+ Users, Media & Feeds)

+ Celebrity Fan-Out Explained

Instagram combines almost every HLD building block at massive scale. Traffic enters through Global DNS + CDN Edges, passes through a WAF, Rate Limiter, and API Gateway (using session tokens after login), and splits across specialized microservices using three API styles: REST for uploads/standard actions, GraphQL for pulling exact profile fields, and WebSockets for DMs, Live video, and instant notifications.

1. Uploading a ReelAsync Media Pipeline

Raw phone videos are huge and unoptimized. After upload via REST, an async pipeline runs:

  • Safety Check: Scans for spam, nudity, or policy violations.
  • Transcoding: Converts video into 360p, 480p, HD, and 4K copies for smooth playback on any mobile network, plus detects audio tracks.
  • Publish: Saves the video files to Object Storage (S3), pushes them onto the CDN, and stores the reel ID + URL in the database.
2. Feed Fan-Out & CelebritiesHybrid Push / Pull

How does a new post appear in followers' feeds quickly — without melting the system when Virat Kohli (300M followers) posts?

  • Normal Users (Push / Fan-Out on Write): Background workers push the new post ID into each follower's pre-built Redis feed, making feed loading instant.
  • Celebrities (Pull / Fan-Out on Read): Writing 300M feed entries is way too slow. Instead, celebrity posts are fetched and merged live when a follower opens the app!
  • Instant Likes: The heart turns red immediately in your UI while the total like count updates asynchronously in the background (Write-Back / BASE).
3. Recommendation Engine4-Stage ML Funnel

All engagement signals (5-second skip vs. full watch + like + comment) flow into a Data Lake powering 4 stages:

  • Retrieval: Pull candidate reels matching user interests.
  • Filtering: Drop spam, already-watched, or muted creators.
  • Ranking: Score posts by predicted watch time & engagement.
  • Re-ranking: Deliberately mix in variety so one viral creator doesn't flood every single slot in your feed.

Case Study 2: IRCTC Tatkal — Surviving a 10–20× Traffic Surge

Scalability + Strict Concurrency Control

At 10:00 AM sharp, lakhs of passengers and ticket agents rush IRCTC for a tiny pool of Tatkal seats. The exact same design pattern powers Amazon Big Billion Days and Hotstar IPL finals, built around two pillars: Auto-Scaling (absorbing the wave) and Locking (ensuring two people never book the same seat).

1
Offload Static & Auto-Scale Train numbers and timetables are served straight from the CDN. Ahead of 10:00 AM, auto-scaling spins up extra backend servers (e.g., 10 → 30 instances) behind the Load Balancer.
2
Stateless Gateway & Bot Defense A stateless API Gateway verifies logins and applies strict rate limiting so automated dealer bots cannot flood out normal travelers.
3
Redis Shields the Reads Most early traffic is people refreshing seat availability. A fast Redis cluster serves those reads so the primary SQL database isn't crushed before booking even begins.
4
Seat Lock (10 Seats vs 10k Buyers) Everyone can read availability simultaneously, but booking acquires a timed lock on the seat (ordered by timestamp or priority rules like senior citizens). Nobody else can grab it while locked.
5
Pay, Rollback & Async Ticket If payment completes in time, the ACID booking commits and SMS/Email confirmations go out asynchronously via Kafka/RabbitMQ. If payment fails or times out, the transaction rolls back and the seat lock releases for the next buyer.

  • 4. Deep Dive & Bottlenecks (20 min): Proactively call out weak spots — single points of failure, sharding keys, celebrity/hot-key skew, locking under contention, and observability.
