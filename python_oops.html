Foundations — Why OOP, Classes & Objects

Generality → Specificity · Blueprint · Method vs Function
The One-Line Idea
OOP lets you invent your own custom data types. You could build LinkedIn, OYO, or Ola using only generic lists, dicts, and strings — just like you could do security testing on plain Windows. But OOP moves you from generality to specificity (like using Kali Linux for security): you create dedicated types like User, Atm, or Train that mirror the real world and keep large codebases clean and easy to extend.

In Python, Everything Is an Object

Data Type = Class · Variable = Object

Try calling [1, 2, 3].upper() or "hello".append(4) in Python and look closely at the error: 'list' object has no attribute 'upper' and 'str' object has no attribute 'append'. Even integers, lists, strings, and functions are objects created from built-in classes (type(5) prints <class 'int'>). Python simply gives built-in types shortcut syntax called object literals (L = [1, 2] instead of L = list([1, 2])) so writing everyday code feels effortless.

Class = Blueprint · Object = Real Instance1 Class → Many Objects

A class defines the rules for how an object will look and behave — writing the class takes the real design effort. An object is a concrete instance built from that blueprint (just one line: sbi = Atm()).

  • Data (Attributes / Properties): What the object has (nouns) — e.g., a Car has color, engine, mileage; an Atm has pin and balance.
  • Behavior (Methods): What the object does (verbs) — e.g., calculate_speed(), deposit(), withdraw().
  • Naming Rules (PEP 8): Classes use PascalCase (BankAccount); variables & methods use snake_case (check_balance).
Function vs. Method & UML BoxInterview Favorite

Why do we write len(L) for length, but L.append(5) to add an item? Because len() is a standalone function usable on many types, whereas append() is a method defined inside the list class — only a list object can call it.

Constructor, self & Magic Methods

__init__ · Why self Exists · Dunder Methods · Fraction Class

Constructor (__init__) & Why self Exists

The two biggest beginner stumbling blocks, simplified
What Is __init__ Really For?Auto-Runs on Creation

__init__ is Python's constructor — a special method that runs automatically the instant you create an object (sbi = Atm()). Unlike Java/C++, its name is always __init__, never the class name.

Why does it exist? It runs essential setup code you never want to leave up to the user clicking a button — initializing attributes, connecting to a database, loading config, or opening a network session. (In the lecture's philosophical analogy: if God wrote the Human class, breathing is a method you control, while mortality sits inside __init__ — set automatically the moment an object is born.)

Demystifying selfself = Current Object

If you print id(self) inside Atm and then print id(sbi) outside, both memory addresses are identical. When you create hdfc = Atm(), self points to hdfc. So self is simply whichever object is currently calling the method.

  • Why pass self to every method? Because Python enforces a golden rule: only an object can access a class's data and other methods — even one method inside the class cannot call another method directly without self!
  • When you run sbi.deposit(), Python silently translates it into Atm.deposit(sbi). Forgetting self raises: takes 0 positional arguments but 1 was given.
Fun fact: self is a convention, not a keyword — you could name it this or me, though every Python developer uses self.
atm_basic.py — Class, Constructor & Independent Object State
class Atm:
    def __init__(self, pin, balance=0):
        # Instance variables live inside each object independently
        self.pin = pin
        self.balance = balance

    def deposit(self, pin, amount):
        if pin == self.pin:
            self.balance += amount
            print(f"Deposited ₹{amount}. New balance: ₹{self.balance}")
        else:
            print("Invalid PIN")

    def withdraw(self, pin, amount):
        if pin != self.pin:
            print("Invalid PIN")
        elif amount > self.balance:
            print("Insufficient funds")
        else:
            self.balance -= amount
            print(f"Withdrew ₹{amount}. Remaining: ₹{self.balance}")

sbi  = Atm("1234", 5000)   # self refers to sbi
hdfc = Atm("9999", 100000) # self refers to hdfc (completely separate state!)
sbi.withdraw("1234", 2000) # Remaining: ₹3000; hdfc is still ₹100000

Magic (Dunder) Methods — Teaching Python How Your Type Works

Dunder = Double Underscore (__name__) Enhanced: Chaining Fixed

Magic methods are predefined methods surrounded by double underscores (like __init__, __str__, __add__). You don't call them directly — Python triggers them automatically on specific events, letting your custom objects behave seamlessly like built-in types (printable with print(), addable with +, measurable with len()).

Magic MethodTriggered Automatically When...Example Use
__init__An object is created: obj = MyClass()Initialize instance attributes & setup resources.
__str__You call print(obj) or str(obj)Return a clean human-readable string (e.g., "3/4" instead of memory address).
__add__ / __sub__You write x + y or x - yDefine custom addition/subtraction between two objects.
__mul__ / __truediv__You write x * y or x / yDefine custom multiplication and division.
__eq__ / __lt__You write x == y or x < yCompare custom objects by value instead of memory identity.
fraction.py — Building a Custom Data Type (Returns Fraction for Chaining)
from math import gcd

class Fraction:
    def __init__(self, num, den):
        if den == 0:
            raise ValueError("Denominator cannot be zero")
        common = gcd(num, den)
        self.num = num // common
        self.den = den // common

    def __str__(self):
        return f"{self.num}/{self.den}"

    def __add__(self, other):
        # Return a new Fraction (not a string!) so x + y + z chaining works
        return Fraction(self.num * other.den + other.num * self.den, self.den * other.den)

    def __sub__(self, other):
        return Fraction(self.num * other.den - other.num * self.den, self.den * other.den)

    def __mul__(self, other):
        return Fraction(self.num * other.num, self.den * other.den)

    def __truediv__(self, other):
        return Fraction(self.num * other.den, self.den * other.num)

x, y = Fraction(3, 4), Fraction(1, 2)
print(x + y)          # 5/4
print(x + y + x)      # 2/1  (works because __add__ returns a Fraction!)
Small Fix
In the lecture, __add__ returned a formatted string like "10/8". Returning a new Fraction object instead (and reducing via gcd) lets you chain operations like (x + y) * z cleanly, just like real numbers.

Encapsulation & Data Protection

Private (__var) · Name Mangling · Getters/Setters · @property

Why Hide Data? (The Junior Developer Problem)

Never expose raw variables to arbitrary mutation

If sbi.balance is public, any other developer on your team can accidentally run sbi.balance = "hello" or set it to -99999, instantly crashing withdraw() later. Encapsulation means bundling data with the methods that safely control it — keeping attributes private and letting outside code read or modify them only through validated gates (getters/setters or Python's @property).

How __private Works — Name ManglingNothing Is Truly Private

Prefixing an attribute or method with double underscores (self.__balance) hides it from normal autocomplete and direct access. Behind the scenes, Python silently renames it to _ClassName__balance (e.g., _Atm__balance) — a trick called Name Mangling.

  • Tricky Bug to Watch For: Writing sbi.__balance = 0 from outside does not edit the real private balance — it quietly creates a brand-new public variable literally named __balance while _Atm__balance stays untouched!
  • "We are all consenting adults": Someone can still reach sbi._Atm__balance if they insist. Python discourages accidental misuse rather than putting up iron locks.
Access Conventions in PythonPublic · Protected · Private
  • balance (no underscore): Public — free for anyone to read and modify.
  • _balance (single underscore): Protected (by convention) — "internal use or subclasses only, please don't touch from outside."
  • __balance (double underscore): Private — triggers Name Mangling (_Atm__balance) to prevent accidental overrides or outside access.
Pythonic Upgrade: Instead of Java-style get_pin() / set_pin(), modern Python uses @property so users write clean sbi.pin = "5678" while validation still runs automatically!
encapsulation.py — Private Data + Pythonic @property Validation
class Atm:
    def __init__(self, pin, balance=0):
        self.__pin = pin           # stored internally as _Atm__pin
        self.__balance = balance   # stored internally as _Atm__balance

    @property
    def pin(self):                 # Getter: called when reading sbi.pin
        return self.__pin

    @pin.setter
    def pin(self, new_pin):        # Setter: runs validation on sbi.pin = ...
        if isinstance(new_pin, str) and len(new_pin) == 4 and new_pin.isdigit():
            self.__pin = new_pin
        else:
            raise ValueError("PIN must be a 4-digit string")

sbi = Atm("1234", 5000)
sbi.pin = "5678"     # Runs @pin.setter cleanly!
# sbi.pin = 99       # Raises ValueError — invalid data is blocked

Objects in Memory, Collections & Static Members

Reference Variables · Mutability · Instance vs Class/Static

Reference Variables, Pass-by-Reference & Mutability

Custom objects behave like lists (mutable) Clarification: Set Hashability

When you write sbi = Atm(), the object is created in memory, and sbi is actually a reference variable holding that object's memory address (not the object itself). If you just write Atm() without saving it to a variable, the object gets created and immediately lost because nothing points to it.

Passing Objects to FunctionsAliasing & Mutability

Because custom objects are mutable and Python passes object references into functions, modifying an object's attributes inside a function permanently edits the original object outside too (same memory id()).

  • Mutable danger (lists / custom objects): If you don't want a function to alter your original list or object, pass a copy (e.g., L[:] or copy.copy(obj)).
  • Immutable types (int, str, tuple): Reassigning inside a function creates a new object, leaving the caller's variable untouched.
Storing Objects in CollectionsList · Tuple · Dict · Set

Custom objects are first-class citizens — you can store them in lists, tuples, or dicts and loop over them effortlessly (for c in [c1, c2, c3]: c.intro()).

Subtle Correction on Sets: The lecture suggests custom objects can't go into a set because they're mutable. Actually, Python classes are hashable by default (by memory identity id), so {c1, c2} works! They only become unhashable if you define a custom __eq__ without also defining __hash__.

Instance vs. Class (Static) Variables & Methods

Shared across all objects (e.g., auto-incrementing customer ID) + @classmethod Added

Suppose every new bank customer must automatically get a sequential serial number: Customer 1 gets 1, Customer 2 gets 2, Customer 3 gets 3. An instance variable (self.sno) resets for each object, so it can't track the global count. Instead, you create a Class / Static Variable outside __init__ — shared by the entire class and accessed as ClassName.var.

Method / Variable TypeDecorator & 1st ParamWhat It AccessesWhen to Use
Instance Method None · (self) Reads/modifies a specific object's state (self.balance). Default for object behaviors like withdraw() or intro().
@classmethod @classmethod · (cls) Reads/modifies class-level state (cls.__counter); works cleanly with inheritance! + Best practice Accessing/updating class counters or writing alternative constructors (e.g., User.from_json()).
@staticmethod @staticmethod · none No self or cls — pure utility helper grouped inside the class namespace. Stateless helpers like Atm.is_valid_pin(pin) that can be called without creating an object.
static_and_class.py — Auto-Increment Serial Number
class Customer:
    __counter = 1   # Class (static) variable — ONE shared copy for all objects

    def __init__(self, name):
        self.name = name
        self.sno = Customer.__counter     # Instance variable — unique per object
        Customer.__counter += 1

    @classmethod
    def get_next_sno(cls):                # Works cleanly even on subclasses
        return cls.__counter

    @staticmethod
    def is_valid_name(name):              # Utility: needs neither self nor cls
        return isinstance(name, str) and len(name.strip()) > 0

c1, c2 = Customer("Ankita"), Customer("Nitish")
print(c1.sno, c2.sno)                     # 1 2
print(Customer.get_next_sno())            # 3 (called without any object!)

Class Relationships & Inheritance

Aggregation (Has-A) · Composition · Inheritance (Is-A) · super() · MRO

Aggregation (Has-A) vs. Composition vs. Inheritance (Is-A)

+ Composition Added

Real applications aren't just one giant class — they are networks of smaller classes working together. Before connecting two classes, ask one simple English question: "Does A have a B, or is A a kind of B?"

Aggregation (Has-A · Loose)Customer ◇── Address

One class holds a reference to another object created outside. Example: a Customer has an Address object. If the customer is deleted, the address object can still exist independently.

Key pattern: When customer.edit_profile() updates city/pin, it delegates the change to self.address.change_address(...).
Composition (Owns-A · Tight)House ◆── Room

A stricter form of Has-A where the child object is created inside the owner and cannot meaningfully live without it. Delete the House (or Order), and its Rooms (or OrderItems) disappear too.

Design wisdom: "Favor composition over inheritance" when you only need to reuse behavior, not build a rigid family tree.
Inheritance (Is-A)SmartPhone ──▷ Phone

A child class automatically gains the parent's attributes and methods, eliminating duplicated code (DRY). Example: both Student and Instructor are a User, so login/register live once in User.

Rule of thumb: Inheritance flows strictly downward — a child gets parent features, never the reverse.

What Gets Inherited & How super() Works

Correction: Python super() Placement
4 Rules of Inheritance in PythonKeep These Straight
  • Inherited: Parent's constructor (if child doesn't define its own), all public/protected attributes, and all non-private methods.
  • NOT directly accessible: Parent's __private members (name-mangled to _Parent__var).
  • Child Constructor Override: If the child defines its own __init__, the parent's __init__ does not run automatically — meaning parent attributes won't even exist unless you explicitly call super().__init__(...)!
  • Method Overriding: If both parent and child define buy(), calling child.buy() executes the child's version.
super() — Calling the Parent CleanlyMethods & Constructors Only

super() lets a child class invoke a parent's method or constructor (e.g., super().__init__(price, brand) to avoid repeating setup, or super().buy() to extend instead of completely replacing parent behavior).

  • super() only works inside a class (never from outside) and is used for methods/constructors, not instance attributes.
  • Subtle Fix vs. Lecture: In Java, super() must be the very first line of a constructor. In Python, it's good practice to call it early, but Python allows statements before super().__init__() (like validating inputs first)!
inheritance_super.py — Reusing Parent Constructor & Extending Methods
class Phone:
    def __init__(self, price, brand):
        self.price = price
        self.brand = brand

    def buy(self):
        print(f"Buying a {self.brand} phone for ₹{self.price}")

class SmartPhone(Phone):
    def __init__(self, price, brand, os, ram):
        super().__init__(price, brand)   # Delegate shared fields to Phone
        self.os = os
        self.ram = ram

    def buy(self):
        super().buy()                    # Run parent logic, then extend it
        print(f"Specs: {self.os}, {self.ram}GB RAM")

s = SmartPhone(50000, "Apple", "iOS", 8)
s.buy()

5 Types of Inheritance & MRO (Diamond Problem)

How Python resolves conflicts in Multiple Inheritance
TypeStructureExample & Key Detail
SingleParent → ChildPhone → SmartPhone. Simplest and most common hierarchy.
MultilevelGrandparent → Parent → ChildProduct → Phone → SmartPhone. Child inherits down the entire chain.
Hierarchical1 Parent → Many ChildrenUser → Student and User → Instructor sharing common login logic.
Multiple(Parent1, Parent2) → Childclass SmartPhone(Phone, Product). Supported in Python (disallowed for classes in Java).
HybridCombination of the abovee.g., Diamond shape: A → (B, C) → D. Resolved cleanly using Python's MRO.
MRO (Method Resolution Order)
If class SmartPhone(Product, Phone) inherits a buy() method from both parents, which one wins? Python follows MRO (C3 Linearization) — checking left-to-right in the inheritance tuple: Product.buy() wins here, whereas (Phone, Product) picks Phone.buy(). You can inspect any class's exact lookup order anytime via SmartPhone.mro().

Polymorphism — One Interface, Many Forms

Overriding · Overloading · Operator Overloading · Duck Typing

Polymorphism literally means "many forms" — the same method name or operator behaves appropriately depending on what kind of object you give it. Think of how + adds numbers (2 + 3 == 5), joins strings ("a" + "b" == "ab"), and merges lists ([1] + [2] == [1, 2]).

FormHow It Works in PythonQuick Example
Method Overriding A child class redefines a method already present in its parent to provide specialized behavior (runtime polymorphism). Phone.buy() prints generic checkout; SmartPhone.buy() prints specs & warranty too.
Method Overloading Not native like Java/C++ Defining two area() methods in one Python class simply makes the second overwrite the first! Instead, Python achieves the same clean API with default arguments or *args. def area(self, a, b=0):
area(4) → circle 3.14 * 4 * 4;
area(4, 5) → rectangle 4 * 5.
Operator Overloading Giving standard operators (+, -, *, ==) custom meaning for your own classes by implementing magic methods (__add__, __eq__). Fraction(3, 4) + Fraction(1, 2) triggers __add__ and returns 5/4.
Duck Typing + Pythonic Core "If it walks like a duck and quacks like a duck, treat it as a duck." Functions care only whether an object has the needed method — not its parent class! Any object implementing .pay(amount) (UPI, Card, Crypto) works inside checkout(payment) without requiring a shared base class.

ABC · @abstractmethod · Encapsulation vs Abstraction · Mini Projects

Abstraction — Hiding Complexity Behind a Contract

+ Missing 4th Pillar Added

The lecture briefly introduced Abstraction as a pillar at the start, so here is how it actually works in Python. Abstraction hides internal implementation details and exposes only the essential operations a user needs — like driving a car using the steering wheel and brake pedal without knowing how fuel injection works. In Python, you enforce an architectural contract using Abstract Base Classes (ABC and @abstractmethod): no one can instantiate the abstract parent directly, and every child class must implement the required methods.

abstraction_abc.py — Enforcing a Contract
from abc import ABC, abstractmethod

class BankApp(ABC):
    def database(self):
        print("Connected to bank database")

    @abstractmethod
    def security(self):
        pass  # Every subclass MUST implement this!

class MobileApp(BankApp):
    def security(self):
        print("Biometric + OTP verification")

# app = BankApp()    # TypeError: can't instantiate abstract class
m = MobileApp()      # Works because security() is implemented
m.database()
m.security()
Encapsulation vs. AbstractionMost Confused Pair
  • Encapsulation (Data Hiding — How): Wraps data + methods together and protects attributes from invalid outside modification using __private and @property.
  • Abstraction (Implementation Hiding — What): Focuses on the high-level blueprint/interface — showing what an object can do while hiding how it does it internally, enforced via ABC.
Quick Memory Hook: Encapsulation puts a protective capsule around your data; Abstraction gives you a clean dashboard hiding the engine underneath.
